# close 直前コメントのテンプレ

close（= マージ成功）の直前に、そのチケットで**何をどう確かめたか**を台帳へ残す。

なぜ: コメントが自由文だと「何を・どのコマンドで・どの exit で検証したか」「PR / CI の URL」
「レビューで何を直したか」が残らず、引き継ぐ次のセッションは**再検証するか、信じるか**の
二択になる（実測: close 理由の中央値 17 字、PR URL の無い close が常態）。定型があれば人だけ
でなく機械（Stop hook の「痕跡があるか」判定、Hygiene の「close 済みだが PR/検証記録なし」）も
証拠の有無を判定できる。

## 手順（SKILL.md 規律4 手順3 の実体）

```bash
bd comment <id> "<下のテンプレで書いた本文>"
# → マージ成功を確認してから bd close <id>（close はマージ後だけ — 規律4 手順2）
```

## テンプレ

```
検証: <コマンド> exit=<n> (<ISO 日時>, <実行した worktree/ブランチ>)
PR: <url>  CI: <run url または「未使用」>
レビュー: <モデル> 指摘 <n> 件 / 採用 <m> 件（不採用の理由は 1 行ずつ）
未了: <残作業チケット ID か「なし」>
```

## 書き方の規律

- **`PR:` 行を必ず含める。** 行頭キー `PR:` は人の可読性のためだけでなく、機械の検索キーでも
  ある（Stop hook が「チケットに痕跡を残さず終わろうとしている」を判定し、Hygiene が「close
  済みだが PR/検証記録なし」を検出するのに使う）。PR を使わないフロー（検証コントラクトの
  `prFlow` が `direct` / `none`）なら `PR: なし (prFlow=<値>)` と明示する。空欄・省略にしない。
- **`検証: … exit=` に書いてよいのは、自分がこのセッションで実行した検証だけ。** 委譲先の
  「全部通りました」を転記しない（[verification.md](verification.md) の独立検証規律）。実行した
  worktree / ブランチまで書くのは、別ディレクトリ・古い成果に対する実行を後から見分けるため。
- **exit は検証コマンド自身のもの**を書く。ラッパーやバックグラウンドジョブの終了コードは検証
  失敗を 0 に化けさせる（[failure-catalog.md](failure-catalog.md) の verify-exit-masked）。
- **レビュー行は「指摘 n 件 / 採用 m 件」まで書く。** 全件採用でも `n 件 / n 件` と書く。指摘を
  不採用にしたなら理由を 1 行ずつ添える — 採否の最終裁定は依頼した側にあり、その根拠が残る。
  レビューを回していないなら `レビュー: なし` と明示する（空欄にしない）。
- **未了はチケット ID で書く。** 「一部残あり」のような自由文にしない。残作業が無いなら「なし」
  と明示する。派生チケットを起票したなら `bd create ... --deps discovered-from:<このチケット>`
  で来歴を辺として残す（規律4 手順5）。
- 4 行に収まらない詳細（設計判断の経緯、失敗の分析、次セッションへの申し送り）は、この定型の
  **後ろ**に段落として足してよい。定型の 4 行を削らないことだけ守る。

## 記入例

```
検証: npm run verify exit=0 (2026-09-04T12:34:56Z, .claude/worktrees/bd-1234 / bd/bd-1234)
PR: https://github.com/example/repo/pull/42  CI: https://github.com/example/repo/actions/runs/99
レビュー: fable 指摘 3 件 / 採用 2 件（不採用: エラー型の統合は別チケット bd-1240 へ切り出し）
未了: bd-1240（エラー型の統合）
```
