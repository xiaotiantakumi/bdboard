# ハーネス・ブラシュアップ手順（規律5の詳細）

失敗をこの skill 本体へ還流させるための手順。SKILL.md 規律5 の手順1〜4（検知・証拠保全・
起票・層判定）の後、このファイルの §2 以降を実行する。

## 役割分担 — どの仕組みが何を担うか

同種の仕組みが複数あるため、先に守備範囲を確定しておく（重複記録・書き場所の迷いを防ぐ）:

| 仕組み | 性質 | 担当 |
|---|---|---|
| この protocol + failure-catalog | **イベント駆動・プロジェクト内** | 失敗が起きたその時に、教訓を repo 内の skill へ還流する |
| グローバル orchestration skill の `reference/lessons-learned.md` | イベント駆動・プロジェクト横断 | プロジェクト非依存の教訓（委譲・並列運用の一般則）のケーススタディ |
| グローバル harness-review skill | 定期・ログ駆動 | 過去ログ全体から摩擦を発掘する棚卸し。個別失敗の即時記録は担わない |
| `bd remember` | 暫定メモ | skill へ還流するまでの**一時置き場**。恒久の正本にしない（下記 §6） |

**正本はこの repo の skill**（この段落はパック正本を編集できる bdboard repo 内での規律。
注入先プロジェクトでは先に [layering.md](layering.md) の層判定に従う — 「写す先」は
project-harness、汎用の教訓は harness-upstream チケット）。このプロジェクトの作業に
関わる教訓は、グローバル skill や
bd memory に既にあっても**この repo の skill 側へ写して自己完結させる**（[layering.md](layering.md)
冒頭「skill 単体で成立する」のとおり — グローバル資産を持たないマシン・エージェントでも
規律が成立すること）。グローバル lessons-learned や bd memory は出典・参考として引いてよいが、
**本則の置き場（§3）にはしない**。こうしてブラシュアップの1件1件が PR として GitHub の
履歴に積まれ、「ハーネスのバージョンアップ」が差分・レビュー付きで追跡できる状態を保つ。

## §1. トリガー判定 — ハーネス失敗か、そうでないか

**ハーネス失敗**（この protocol の対象）: 「作業の回し方」の欠陥に起因するもの。

- 排他の破れ（同一チケット二重着手、worktree のネスト/誤削除、成果の上書き・消失）
- 規律・規約どおりに実行したのに事故った（ルールの誤り、未カバーの穴）
- ルールは存在したが想起されず・曖昧で守られなかった
- skill に書かれたコマンド・手順が現バージョンのツールで動かなかった
- ブロッキング（回答待ち・ロック保持・無限リトライ）でセッションや他セッションが停止した

**対象外**:

- プロダクト自体のバグ → 通常の bug チケットへ（`bd create --type=bug`）
- 一過性の外部障害（GitHub 障害・ネットワーク断）→ ただし「障害時の振る舞い」に改善余地が
  見つかったなら、その部分はハーネス失敗として扱う（例: worktree-pr-flow.md の CI 障害時手順）
- 単発のヒューマンエラーで、ルール化しても防げないもの → 無理にルールを増やさない（§4）

迷ったら「**別セッションが同じ状況に置かれたら、同じ失敗をするか？**」で判定する。
Yes ならハーネス失敗。

ハーネス失敗と判定しても、**その場で直せないものは起票して現作業へ戻る**。失敗対応のために
現チケットを放置しない（SKILL.md 規律3 と同じノンブロッキング原則）。

## §2. 根本原因の4分類

証拠が揃ったら、まず失敗を次の4つに分類する。分類によって直すものが変わる:

| 分類 | 意味 | 直すもの |
|---|---|---|
| **A. ルール不在** | この状況を扱う規律がそもそも無かった | 新しい規律・手順を追加する |
| **B. ルール誤り** | 規律どおりに動いて事故った | 規律の内容を訂正する（誤った規律は無いより悪い — 最優先で直す） |
| **C. ルール曖昧** | 規律はあるが解釈が割れた・条件が不明確だった | 文言を具体化する（コマンド例・判定基準・実測値を足す） |
| **D. ルール不遵守** | 規律は正しかったが従わなかった | **ルールを増やさない。** なぜ想起されなかったかを直す |

**D の扱いが最重要**: 不遵守のたびにルールを追記すると skill が肥大化し、かえって全ルールの
想起率が下がる（それ自体が D を増やす悪循環）。D では次を疑う:

- 配置が悪い — 実行時に読む場所（該当手順の直中）にルールが無く、離れた場所にあった
  → ルールを実行地点へ移す/該当手順からリンクする
- 長すぎて読み飛ばされた → 本文を圧縮し詳細を reference へ落とす
- トリガーが暗黙 — 「このときに読む」が書かれていない → 手順側に照合ステップを明記する
- 記録場所が揮発 — bd memory やチャット履歴にしか無かった → skill/規約へ還流する（§6）

## §3. 教訓の配置先決定表

**前段: まず [layering.md](layering.md) で編集する層を決める。** 注入先プロジェクトに
居るなら、この表の「SKILL.md / reference」は project-harness 側への読み替えになり、
汎用の教訓は harness-upstream チケットで運ぶ（表を直接適用できるのは、パック正本を
編集できる bdboard repo 内だけ）。

一つの教訓の**本則は一箇所**にだけ書く。他はポインタ。配置は上から順に判定:

| 条件 | 配置先 |
|---|---|
| セッションの「回し方」の手順そのものが変わる | SKILL.md 本文（該当規律に追記 or 新規律） |
| 既存の手順詳細（worktree/PR、lease、検証、質問）の追補 | 該当する既存 reference |
| プロジェクト固有の値・コマンド・環境の事実 | プロジェクトの CLAUDE.md（skill には書かない — SKILL.md 前提節のとおり） |
| 上のどれでもない・単発の事例知識 | failure-catalog.md のエントリ自身が本則 |

配置先がどこであっても、**failure-catalog.md にはエントリを必ず置く**（本則が他所なら
「本則の所在」ポインタ付きで）。カタログが唯一の全量索引になる。本則の置き場は常に
**この repo 内**（SKILL.md / references/ / CLAUDE.md のいずれか）— グローバル skill や
bd memory を本則にしない（役割分担の節を参照）。教訓がプロジェクト非依存の一般則でも
あるなら、repo 内へ置いた上で、グローバル orchestration skill の lessons-learned.md への
**転記を追加で**行ってよい（グローバル資産の編集は要ユーザー確認）。

## §4. ルール追加の抑制基準

ルールは追加するほど守られなくなる。追加前に3問すべて Yes であることを確認する:

1. 同じ失敗が**再現しうる**か（構造的な原因があるか。偶発なら記録だけにする）
2. ルールで**機械的に防げる**か（判定基準・コマンドの形で書けるか。心構えはルールにしない）
3. 既存ルールの**訂正・移動・具体化で足りない**か（§2 の B/C/D で済むなら追加しない）

No が混ざるなら、failure-catalog.md へのエントリ追加（事例として記録）に留める。

## §5. Fable で固める — 検討とレビューゲート

分類（§2）と配置（§3）の検討、および反映案の作成は **Fable の最大熟考**で行う:

- 議長自身が Fable ならそのまま検討してよい。そうでなければ `Agent` の `model: "fable"`
  （選べなければ `model: "opus"` にフォールバックし、prompt で最大熟考を指示）へ委譲する。
- 検討に渡す入力: 証拠（SKILL.md 規律5 手順2）、failure-catalog.md の既存エントリ
  （重複・関連の照合用）、変更対象ファイルの現物。
- **この protocol 起点でハーネス規律（本 skill、および CLAUDE.md の運用規約部分）を変更する
  PR は、実装者と別の Fable サブエージェントによる独立レビューをマージ前に通す**（通常の
  機能 PR に伴う CLAUDE.md の軽微な追従までは対象にしない）。レビュー観点:
  (a) 分類と配置は §2/§3 に合っているか、
  (b) 既存規律と矛盾・重複していないか、(c) 追加は §4 の3問を満たすか、(d) 文言は実行時に
  機械的に従える具体性か。
- 採否の最終裁定は議長が持つ（レビューの指摘を鵜呑みにしない — verification.md と同じ原則）。

## §6. 反映 — 通常の PR フローに載せる

- skill は repo 管理ファイルなので、反映は規律2/4 の worktree + PR フローそのまま
  （`harness` ラベルのチケットに紐づける。ユーザーが「チケット不要」と明示した場合を除く）。
- **同じ PR で failure-catalog.md のエントリも追加/更新する**。後追いに分離しない
  （分離した瞬間に散逸が始まる — CLAUDE.md のヘルプ追従ルールと同じ動機）。
- `bd remember` に暫定記録した教訓を skill へ還流したら、メモリ側は「skill へ還流済み
  （参照: <ファイル>）」へ `bd remember --key <key>` で更新するか `bd forget` する。
  二重の正本を残さない。ただし **failure-catalog.md が出典として引いているキーは
  forget しない**（出典参照が宙に浮く）— スタブへの更新側を使う。

## §7. アンチエントロピー — 台帳と skill を腐らせない

- **SKILL.md 本文は規律の骨格だけ**を保つ。目安は **1規律 25 行以内・SKILL.md 全体 8192
  バイト以下**、各規律は「なぜ（3行以内）/ 手順（番号付き・1行ずつ）/ 詳細への参照」の
  3部構成（bdboard-pkr6.7 の骨格化で確定）。超え始めたら、規律を削るのではなく詳細を
  reference へ落とす方を先に検討する。**予算を超えたときは文言を縮めて詰め込まず、最も
  長い規律の手順を1本まるごと reference へ落とす**（縮めるほど手順は曖昧になり、D（不遵守）
  の温床になる）。
- failure-catalog.md のエントリは**1件5行以内**。長くなる分析は本則側（reference 等）へ。
- 新エントリ追加時に同カテゴリの既存エントリを読み、重複していれば統合、矛盾していれば
  古い方を訂正する（追記だけして放置しない）。
- ルールが指す前提（ツールのバージョン・コマンド・パス）が変わって成立しなくなったら、
  そのルールは**削除または訂正**する。成立しない古いルールを残すことは D（不遵守）の温床。
- 台帳全体の定期棚卸し（未使用ルールの発掘・統廃合）はグローバル harness-review skill の
  定期実行に委ねる。この protocol はイベント駆動の還流だけを担う。
