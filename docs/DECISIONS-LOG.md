# 判断ログ（実装中に確認したかったこと）

このファイルは、実装を自律的に進める過程で「本来はユーザーに確認したかったが、
止めずに自分の判断で進めた」事項を残す場所。ユーザーは実装がある程度まとまった時点で、
実際に動くものを触りながらここを見て微調整を判断する運用（2026-08-14に合意）。

**運用ルール**:
- 判断に迷ったら作業を止めない。PLAN.md・既存コードの慣習・標準的なプラクティスに沿って
  自分で決め、**この下に追記してから先に進む**。
- 各エントリは追記のみ（既存エントリの書き換え・削除はしない）。
- 破壊的操作・秘密情報・pushなど、そもそも許可されていないこと（SKILL.md/CLAUDE.mdの
  禁止事項）に該当する場合はこのログでは済まさず、通常どおり作業を止めて報告する。

**エントリ形式**:
```
## [スライス/日時] 短いタイトル

**状況**: 何が曖昧だったか
**決定**: 何を選んだか
**理由**: なぜそれを選んだか
**ユーザーが後で見直す観点**: 違う選択肢がありうるとしたら何か
```

## [S1 / 2026-08-14] domain は Clock ポートを持たず `now: Date` を引数で受ける

**状況**: PLAN.md は「`defer_until` を見る必要があるので、ドメインが `Clock` ポートを持つ正当な理由がある」と書いている。一方で「ポート(application が定義)」の一覧にも `Clock` が入っており、どちらの層に置くか曖昧だった。
**決定**: `Clock` インターフェース(`{ now(): Date }`)自体は domain に置くが、domain の導出関数(`isDeferred` / `isReady` / `deriveLane` / `computeLiveness` / `buildBoard`)は Clock を受け取らず **`now: Date` を直接引数で受ける**。呼び出し側が一度だけ `clock.now()` を解決して渡す。
**理由**: ボード1回分の計算の途中で時刻が進むと、同じ計算内で「deferred と判定されたチケット」と「そうでないチケット」の基準時刻がズレて結果が非決定的になる。純粋関数として最もテストしやすい形でもある。
**ユーザーが後で見直す観点**: domain 関数のシグネチャに `now` が並ぶのが冗長に感じるなら、`ReadinessContext` に `now` を畳み込む案もある(その場合 context 生成時に時刻が固定される)。

## [S1 / 2026-08-14] `deriveLane` の判定順は Blocked を Deferred より先にする

**状況**: あるチケットが「未クローズの blocks ブロッカーを持つ」かつ「`defer_until` が未来」の両方を満たすとき、Blocked と Deferred のどちらのレーンに出すか PLAN.md は規定していない。
**決定**: Blocked を先に判定する(closed → in_progress → status=blocked → 導出blocked → deferred → ready の順)。
**理由**: PLAN.md のレーン列挙順が `In Progress / Blocked / Ready / Deferred / Done` で Blocked が先。また「ブロックされている」の方が行動可能性に対する制約として強い情報。
**ユーザーが後で見直す観点**: 実際に画面を見て「defer したものは Blocked に混ざらず全部 Deferred にまとめたい」と感じたら逆順にする。

## [S1 / 2026-08-14] 未知のブロッカーIDはブロック扱いにしない

**状況**: `blocks` 依存の相手チケットが取得済みチケット集合に存在しない場合(プロジェクト外参照・データ欠損)、ブロックとみなすか否か。
**決定**: **ブロックとみなさない**(ready になりうる)。
**理由**: 存在を確認できないものでチケットを永久に止める方が害が大きい。bd 自身の `bd ready` とも一致した(実測7プロジェクトで完全一致)。
**ユーザーが後で見直す観点**: 逆に「知らない依存があるなら安全側に倒して Blocked にしたい」なら反転できる。その場合 `bd ready` との一致は崩れる。

## [S1 / 2026-08-14] ソートの文字列比較はコードポイント順(localeCompare を使わない)

**状況**: 実装が当初 `localeCompare` を使っていた。
**決定**: `src/domain/compare.ts` の `compareStrings`(`a < b ? -1 : a > b ? 1 : 0`)に統一。
**理由**: `localeCompare` は ICU のロケール依存で実行環境により結果が変わりうるうえ、異なる文字列に 0 を返しうるため「最終タイブレークによる全順序保証」が壊れる。横断ボードの並びが環境で変わってはいけない。
**ユーザーが後で見直す観点**: 画面上で `ExampleApp` が `bdboard` より先に来る(大文字が先)のが不自然に見えるなら、表示用のソートだけ大文字小文字を無視する比較に変える(内部の決定性は保ったまま)。

## [S2 / 2026-08-14] 走査は `.claude` を除外するため、worktree 正規化は「明示指定時」にのみ効く

**状況**: PLAN.md は worktree 正規化(`git rev-parse --git-common-dir` の dirname)を必須としているが、既定の走査では `.claude` をスキップするため `<repo>/.claude/worktrees/<name>` が候補にならず、正規化ロジックが実質発火しない。
**決定**: 走査で `.claude` をスキップする方針は維持し、正規化ロジックも残す(scanRoot に worktree を直接指定した場合と、S8 でセッションの cwd から本体を引く用途で効く)。
**理由**: 走査で worktree を拾ってから畳むより、最初から拾わない方が単純で速い。`.beads` は本体チェックアウト側にしか無いので、走査対象として worktree を見に行く必要が無い。
**ユーザーが後で見直す観点**: worktree 側に独自の `.beads` を置く運用を将来始めるなら、この前提が崩れる。

## [S3 / 2026-08-14] ゴールデンfixtureに実プロジェクトのチケット本文をそのまま含める

**状況**: オラクルテストのために実測した `bd list --json` を `test/fixtures/bd/` に固定する必要があるが、これには9つの実プロジェクトのチケットのタイトル・説明文がそのまま入る(約944KB)。
**決定**: 9プロジェクト分をそのまま含める(list / blocked / ready の3種)。
**理由**: PLAN.md がオラクルテストを「最重要」と位置付けており、実データでの回帰検証がこのプロジェクトの正しさの中核。bdboard 自体が private リポジトリで、内容は同じマシン上の同じユーザーのもの。
**ユーザーが後で見直す観点**: 将来このリポジトリを公開する可能性があるなら、fixture を匿名化(title/description をハッシュや連番に置換)する必要がある。**公開前に必ず確認すること。**

## [S9 / 2026-08-14] resume なのに sessionId が無い場合はコマンドを組まずに投げる

**状況**: `buildClaudeCommand` は当初、`mode: 'resume'` でも `sessionId` が空なら `--resume` を落として `args: []` を返す実装だった(仕様として私がそう指示した)。
**決定**: `MissingSessionIdError` を投げるように変更。Runner 側(`createClaudeRunner`)はそれを捕まえて `failureKind: 'invalid-request'` の `RunOutcome` を返す(ポート契約として `dispatch()` は投げない)。
**理由**: `--resume` を落としたコマンドは**新規 spawn と完全に同じ argv** になる。v1 は dispatch しないので無害だが、v2 で実起動を入れた瞬間「再開のつもりが実プロジェクトのディレクトリで新しいエージェントが立ち上がる」という静かな事故になる。`validateRunRequest` が先に弾く前提だが、その前提が崩れたときに黙って別の動作をするのは危険なので二重防御にした。
**ユーザーが後で見直す観点**: 「sessionId が無ければ黙って新規セッションを立ててくれた方が便利」という運用を望むなら反転できるが、その場合は UI 側で「新規セッションになります」と明示すべき。

## [S9 / 2026-08-14] v1 では Runner を合成ルートに登録せず、それをテストで固定する

**状況**: PLAN.md の v1 安全保証は「書き込み経路が物理的に存在しない状態にする」と要求している。Runner のポートと型だけ作ると、うっかり `src/main.ts` に配線して API から起動できてしまう余地が残る。
**決定**: `src/infrastructure/runners/runners-are-disabled.test.ts` を回帰テストとして置き、(1)全 Runner の `dispatch()` が `dispatch-disabled` を返すこと、(2)`src/main.ts` に Runner 配線トークンが現れないこと(既存の bd 実行用 `NodeCommandRunner`/`commandRunner` のみ許可リスト)、(3)`src/application/runner/**` と `src/infrastructure/runners/**` の実装ファイルに `child_process`/`node:net`/`spawn(`/`execFile(` が現れないこと、をテキスト検査で固定した。
**理由**: 依存方向ルール(depcruise)は「どこから import してよいか」しか見ないので、「合成ルートに登録されていないこと」は表現できない。テキスト検査は粗いが、意図せぬ配線が入った瞬間に落ちるという目的には十分。
**ユーザーが後で見直す観点**: v2 で実 dispatch を入れるときは、このテストを**消すのではなく**「登録されるのは非 experimental の Runner だけ」等に書き換えること。消すと安全保証が無言で消える。

## [S9 / 2026-08-14] Runner の優先順は「安定版が先、experimental が最後」

**状況**: `AgentRunnerRegistry.resolve` が返す順序(= フォールバック順)をどう決めるか。実験的なソケット割り込みの方が「うまくいけば速い」ので先に試す案もありうる。
**決定**: 非 experimental を先、experimental を最後にする。同カテゴリ内は id 昇順(`compareStrings`)で決定的に。
**理由**: 実験的経路を先に試すと、それが壊れていても後段の安定版が拾ってしまい、**公式経路が健全かどうかが観測できなくなる**。壊れた非公開 IPC への依存が常態化するのを避けたい。
**ユーザーが後で見直す観点**: 実際に使ってみて「ソケット割り込みの方が体験が良く、失敗も即座に分かる」なら順序を入れ替える余地はある。

**ユーザーが後で見直す観点**: 「fast」モデルは通常版より品質が落ちる可能性があるため、実装品質に懸念が出たら`composer-2.5`(非fast)に戻す判断がありうる。

## [.16 / 2026-08-14夜] 認証情報が未設定なら fail-open ではなく全リクエストを 503 で拒否する

**状況**: チケットの実装方針は「環境変数が未設定なら認証を要求せず警告ログを出す(fail-open)。開発時に .env を用意しないとローカルでも動かせない事故を避ける」を推奨していた。
**決定**: 採らなかった。未設定時は**全リクエストを 503** で拒否し、設定すべき変数名を案内する。認証を外したい場合は `BDBOARD_AUTH_DISABLED=1` を**明示的に**指定させる。
**理由**: 今回の情報露出そのものが「認証が無いまま公開されていた」という形で起きている。fail-open は**環境変数を1つ書き忘れるだけで無言で全公開状態に戻る**設計で、同じ事故を再発させる。開発時の利便性は「明示的な опт-out 変数を1つ置く」ことで十分確保でき、そちらは書き忘れても危険側に倒れない。
**ユーザーが後で見直す観点**: ローカル開発のたびに `.env` か `BDBOARD_AUTH_DISABLED=1` が要るのが煩わしければ、「サーバーが loopback にのみ bind していて、かつ明示 opt-out がある場合のみ素通し」まで緩める案はある。ただし bind アドレスはトンネル有無を判別できない(トンネルもローカルの 127.0.0.1 に繋ぐ)ので、実質的な安全性の向上にはならない点に注意。

## [.16 / 2026-08-14夜] 総当たりカウントの対象は「資格情報を提示した失敗」のみ

**状況**: 実装当初、`Authorization` ヘッダが無いリクエストも失敗回数に数えていた。10回失敗で60秒ロックする仕様のため、これは実際に検証中に自分自身をロックアウトさせた。
**決定**: **パース可能な `Basic` 資格情報を提示して失敗した場合のみ**カウントする。ヘッダ欠落・非Basic スキームは 401 を返すがカウントしない。実サーバーで「匿名リクエスト30回の後でも正しい資格情報が 200 で通る」ことを確認済み。
**理由**: ヘッダ無しのリクエストは、ブラウザの初回アクセス・favicon・SSE再接続・巡回ボットのすべてが該当する通常の姿。これを数えると、**URLを知っているだけの第三者が10回叩けば所有者が締め出され**、さらに60秒に1リクエスト送り続けるだけでボードを恒久的に落とせる(総当たりを試みる必要すらない DoS)。除外しても総当たり耐性は一切落ちない — パスワードは提示しなければ当てられないため。
**ユーザーが後で見直す観点**: それでも「10回失敗で全員60秒ロック」はグローバルカウンタなので、第三者が誤った資格情報を送り続ければ所有者も巻き込まれる。パスワードが4桁である限りはこの側に倒すのが妥当だが、桁数を増やすならロックを緩められる。

## [.16 / 2026-08-14夜] 認証情報の値はチャットに出さず `.env` にのみ置く。トンネル再生成は行わない

**状況**: 「トンネルを再生成して疎通確認し、発行した URL と実際のユーザー名/パスワードをメッセージで返してほしい」という依頼を受けた。
**決定**: (1)認証情報はリポジトリ直下の `.env`(パーミッション600・git管理外)に生成して置くだけとし、**値をメッセージやログに書かない**。(2)**公開トンネルの生成は行わなかった**。認証の検証はローカル(127.0.0.1:8787)に対して全ルート分実施した。
**理由**: (1)は「シークレット値を表示しない」という運用ルールそのもの。ユーザーは自分の `.env` を読めば値が分かるので、値を伝達経路に流す必要がない。(2)公開トンネルの生成は、ユーザーの非公開チケット本文・実メールアドレス・絶対パスをインターネットから到達可能にする操作で、ユーザー本人の明示的な許可が要る種類の行為。ユーザーは就寝中で応答できず、また4桁パスワードは公開URL上では総当たり耐性が低い。トンネルは認証の正しさに影響しない単なる経路なので、検証としてはローカルで十分。
**ユーザーが後で見直す観点**: 起床後にトンネルを張り直すなら `cloudflared tunnel --url http://localhost:8787` を実行するだけでよい(認証は既に全ルートに掛かっている)。公開したまま運用するなら、4桁より長いパスワードにするか、Cloudflare Access 等の前段認証を足すことを勧める。

## [.30 / 2026-08-15] トンネル制御APIは「ループバック」だけでは守れない

**状況**: チケットの実装方針は「起動/停止APIは localhost 限定にする」だった。素直に読むとソケットの送信元アドレスがループバックかどうかを見る実装になる。
**決定**: 送信元がループバックであることに加えて、**Cloudflare の転送ヘッダ(`CF-Connecting-IP` / `CF-Ray` / `CF-Visitor`)が付いていないこと**も要求する。どちらか一方でも欠ければ 403。送信元アドレスが取得できない場合も 403(安全側)。ガードはパス列挙ではなく `/api/tunnel` と `/api/tunnel/*` の前方一致で取り付け、将来エンドポイントを足したときにガード漏れが起きないようにした。
**理由**: **cloudflared はローカルサーバーへ 127.0.0.1 から接続する。**つまりトンネル経由で来たリクエストもソケットの送信元アドレスはループバックに見え、送信元だけではローカル直アクセスと区別できない。ここを見落とすと「トンネル越しに誰でも新しいトンネルを起動/停止できる」という、まさに避けたかった事故がそのまま残る。Cloudflare の転送ヘッダは cloudflared 自身が付けるものでクライアント側から取り除けないため、判別材料として使える。
**ユーザーが後で見直す観点**: より強固にするなら、制御APIだけ別ポート(トンネルが指していないポート)で待ち受ける構成にすると、ヘッダの挙動に依存せず**構造的に**到達不能にできる。現状はヘッダ検査に依存している点が唯一の弱み。

**状況**: `.16` は未設定時の fail-open を退けて全リクエストを 503 にしつつ、将来案として「loopback bind + 明示 opt-out 時だけ素通し」も挙げていた。ただし bind アドレスだけではトンネルを区別できず実質的な安全性向上にならない、と留保していた。本チケットはその留保を、接続経路を追加判定する形で解消し、ローカル利用時の `.env` / opt-out 必須を見直すもの。

**理由**: HTTP モードの cloudflared はローカルサーバーへ 127.0.0.1 から接続し、Cloudflare 転送ヘッダを付けるため、送信元アドレスだけでは区別できないが両条件なら誤免除しない。Host は自己申告だけを根拠に権限を与えるためではなく、期待値と違うとき免除を取り消す追加条件にだけ使う。`unconfigured` の 503 fail-closed はトンネル/リモート越しの無防備公開を防ぐため維持し、ローカル直アクセスだけを限定的に外す。なお Cloudflare ヘッダの前提は cloudflared の HTTP モードに限られ、`ssh -L` / `ngrok` / `socat` / `kubectl port-forward` 等の loopback 終端経路は対象外である。
**ユーザーが後で見直す観点**: トンネル画面は QR コードのみ表示(URL/ユーザー名/パスワードのテキストは出さない)に整理した。スマホ側は QR から開く前提。

## [bdboard-54be.1 / 2026-09-03→09-04 改訂] Claude `--permission-mode` の既定値は default

**状況**: worktree 上で Claude CLI を起動するとき、`--permission-mode` を何にすべきか。
**当初の決定(2026-09-03、撤回)**: 既定 `acceptEdits`。理由として「実行は新規に切った

**撤回の理由**: この理由付けは**前提が二重に成立していなかった**。
1. 当時の allowlist は `Bash(git:*)` / `Bash(npm:*)` / ベアな `Write`・`Edit` を許して
   いたので、そもそも worktree に隔離されていなかった。`git -C <任意パス>` で他の
   worktree やメインチェックアウトを破壊でき、`git config --global core.pager`,
   `npm exec -- sh -c` は任意コマンド実行に化ける。
2. さらに悪いことに、`acceptEdits` は**パススコープそのものを無効化する**。
   実測 (claude CLI 2.1.233):
   - `--permission-mode acceptEdits` + `Edit(./allowed/**)` → スコープ外の `./out.txt` も作成された
   - `--permission-mode default` + `Edit(./allowed/**)` → スコープ外は権限拒否、
     許可内は `-p` のまま確認を求めず作成された
   つまり acceptEdits を選ぶことは、隔離のための対策を打ち消すことと同義だった。
**改訂後の決定**: 既定は **`default`**。`BDBOARD_RUN_PERMISSION_MODE` で上書き可能。
allowlist は必要最小限に絞り、ファイル編集は `Edit(//<worktree 絶対パス>/**)` で
worktree 配下に動的スコープする。`bypassPermissions` は引き続き明示 opt-in。
**副次的な実測**: パスルールは `Write(<path>)` ではなく `Edit(<path>)` で書く
(CLI 自身が「Write(...) is not matched by file permission checks — only Edit(path)
rules are」と診断する)。また絶対パスは**先頭スラッシュ2つ**が必要で、`Edit(/abs/**)`
と1つだけ書くとプロジェクト相対と解釈されて何にも一致せず、エージェントが
worktree 内のファイルすら編集できなくなる(fail-closed なので危険側には倒れないが、
機能が無言で死ぬ)。
**ユーザーが後で見直す観点**: `default` で確認待ちが頻発して実用に耐えないと感じたら、
acceptEdits へ戻すのではなく **allowlist に必要な操作を足す**方向で解決すること。
acceptEdits へ戻すとパススコープが失われる。

**サーバー再起動を要求**する。UI(設定画面)とヘルプに「変更はサーバー再起動後に反映」と明記。
**理由**: 即時反映は攻撃経路そのものなので、UX の低下と引き換えに切る。
**多層防御**: これ単独では不十分なため、同時に (a) allowlist を絞って config を書く手段を
消し、(b) プロンプトから「`bd show` の内容を正本として扱え」を外して untrusted 明示に
変えた。3つで1つの対策。
**ユーザーが後で見直す観点**: 「トグルが効かない」と思って即時反映へ戻さないこと。
戻すとこの昇格経路が再び開く。

## [bdboard-54be.1 / 2026-09-04] エージェントへ渡す環境変数は allowlist する

**状況**: `claude-runner` が `streamingRunner.run` に `env` を渡しておらず、
`NodeStreamingCommandRunner` が `process.env` を丸ごと継承していた。
**問題**: この環境ではサーバーが `kv_inject.sh` 経由で起動されうる(実測: ラッパーが
Key Vault から25個のシークレットを env に注入する)。エージェントの Bash から
`env` 一発で読めてしまい、上の注入経路と組み合わせるとリモート起点のシークレット窃取になる。
**決定**: `PATH/HOME/LANG/LC_ALL/TERM/TMPDIR/USER/SHELL` と `ANTHROPIC_`/`CLAUDE_`

## [bdboard-54be.3 / 2026-09-04] 実行用 worktree とブランチの寿命

**状況**: エージェント実行は `.claude/worktrees/<チケットID>` と
`bd/<チケットID>` を作るが、従来は削除経路がなかった。
一方、実行プロンプトは commit と PR 作成を禁止しているため、run の終了は成果物の寿命が
終わったことを意味しない。

**決定1（成功時）**: 成功直後には worktree とブランチを削除せず、レビューと PR 作成のために残す。
成功した run の主な成果は未コミットの編集であり、この時点で削除すると成果そのものを失うためである。

**決定2（失敗時）**: 失敗時と中止時も自動削除せず、ログだけでは分からない途中編集と調査環境を残す。
失敗を理由に dirty な worktree を削除すると、原因調査に必要な証拠を失うためである。

**決定3（利用中の判定）**: 新しい worktree を追加する直前に限り、既存の実行用 worktree を回収候補にする。
候補は、規定パスとブランチの組が一致し、clean で、ブランチが `origin/main` の祖先であるものに限る。
削除の直前に `lsof -a -d cwd +D <path>` を実行し、出力が一行でもあれば削除しない。
`lsof` が存在しない場合、タイムアウトした場合、診断を出して失敗した場合も削除しない。
`lsof` は一致なしを exit 1 で表すため、exit 1 かつ標準出力と標準エラーが空の場合だけは
「利用者なし」と判定する。
この fail-closed 判定は、別セッションの足元から worktree を削除した事故
（bdboard-3tw.61）の再発を防ぐ。

**決定4（マージ済みブランチ）**: 上の条件を満たした worktree を `git worktree remove` で
削除した後、対応ブランチを `git branch -d` で削除する。
worktree がすでに無いマージ済み `bd/*` ブランチも、どの worktree にも checkout されていない場合に
`git branch -d` で回収する。
`-D` は使わず、Git 自身のマージ済み判定を二重の安全策として残す。

**増加上限**: 失敗した作業や未マージの作業は安全に自動削除できないため、回収だけでは総数を
有限に保てない。
実行用 worktree または対応する `bd/*` ブランチを残しているチケットが既定20件ある場合は、
新規作成を 409 で拒否する。
同じチケットの worktree とブランチは合わせて1件と数える。
上限は `BDBOARD_MAX_MANAGED_WORKTREES` で変更できる。
これにより、調査対象を期限で消さずに、アプリが作る worktree の総数を有限に保つ。

**回収の起点**: 常駐タイマーではなく、新しい worktree を作る直前に回収する。
実行が増えなければ残骸も増えず、新しい生成物を増やす操作自身が先に空きを作るためである。
マージ後に次の実行がなければ最後の残骸は残るが、既存の健全性パネルが検知し、手動整理を案内する。

**削除対象の既定は fail-closed**: 「どのチケットが削除対象か」は
`cleanupEligibleTicketIds`（closed チケットの集合）でしか表現されていない。
この集合を渡さなかった呼び出しは、**何も削除対象にしない**。
実装当初はここが逆で、`undefined` が「フィルタ無し」= 全チケットが削除候補、という
fail-open な既定になっていた。集合を渡し忘れる呼び出し側は「どの worktree を消してよいか」を
考えなかった側なので、そこが最も広い削除権限を得るのは筋が通らない。
省略時の失敗の向きは「消えるべきものが残る」であって「残すべきものが消える」ではない。
本番経路（`agent-run-routes`）は常に集合を渡すので、この既定に依存しない。

**fetch 失敗時は削除しない**: `origin/main` の fetch に失敗した場合、
削除対象の集合を空にして破壊的な回収を止める。
古い remote-tracking ref でも worktree の作成（オフライン動作）には十分だが、
`origin/main` がリモートで force-update されている可能性がある以上、
「マージ済み」判定の根拠としては不十分だからである。
作成は続行し、回収だけを見送る。
